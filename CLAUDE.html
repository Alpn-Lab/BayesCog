    CLAUDE.md — BayesCog

    Authoritative project instructions for Claude. Read this first in any session.

    Note on project type: BayesCog is not a data-analysis research repository. It is an open-access teaching course (a Quarto website) plus an accompanying software/education paper (JOSE/JOSS-style). The “models” here are pedagogical Stan examples bundled with each workshop, not novel research analyses. Apply scientific rigor to the teaching content (the maths, the Stan code, the claims), but there are no original empirical results to protect.

    1. What This Project Is

    BayesCog is a freely available online course teaching Bayesian statistics and hierarchical Bayesian modeling for psychological science, using reinforcement learning as the running example. It is built as a Quarto website (published to GitHub Pages at https://alpn-lab.github.io/BayesCog) and is accompanied by a manuscript (paper.md) submitted as an educational software paper. The course adapts award-winning teaching materials originally created by Lei Zhang (University of Vienna / UKE Hamburg), converted and expanded into a website by Aamir Sohail.

    4. Example Models (pedagogical)

    Each workshop bundles Stan model(s) plus an R driver script. Stan sources live in _scripts/*.stan; compiled models are cached as *.rds; fitted objects (where saved) live in _outputs/*.RData. Scripts come in two versions: a teaching version (e.g. *_main.R, with gaps for students) and a *_master.R completed reference version. Key models: binomial/Bernoulli, linear & polynomial regression with posterior predictive checks, Rescorla-Wagner RL (individual / multi-subject / hierarchical, plus optimized/reparameterized forms), fictitious-update RL, exponential-decay memory, hyperbolic delay-discounting. HDIofMCMC.R and stan_utility.R/stan_diag_tool.R are shared helper scripts copied into several workshops.

    5. Build / Render Pipeline

    This is a website, not an analysis pipeline. The “pipeline” is rendering source → site → deploy.

    1. Author content in workshops/**/qmd/*.qmd, index.qmd, etc.
    2. Preview locally: quarto preview (live-reload in browser).
    3. Render full site: quarto render → outputs to _site/ (git-ignored).
    4. Publish to GitHub Pages: quarto publish gh-pages (manual; the push-based workflow is disabled).
    5. Paper PDF is rebuilt automatically by .github/workflows/draft-pdf.yml whenever paper.md, paper.bib, or assets/fig1.png change on push, and auto-committed as paper.pdf.

    R/Stan code inside workshops is run by students in RStudio; it is not executed during site render (figures are pre-rendered into _plots/ and images/). Quarto uses the .venv Jupyter kernel.

    6. Software & Dependencies

    • Quarto (website engine; pre-release used in CI) with the quarto and include-files.lua filters.
    • R 4.4.1 with renv (lockfile renv.lock). Key packages: rstan, loo, ggplot2, R.matlab, corrr, patchwork, rmarkdown, knitr. Run source("setup.R") once to restore the environment.
    • Stan via RStan for all model fitting (students run this locally).
    • Python/Jupyter (.venv, requirements.txt) — only as the Quarto rendering kernel.
    • Docker alternative: docker pull sohamir/bayescog:latest for a pre-built RStudio environment.

    7. Working on This Project

    • Preview before publishing: always quarto preview to check rendering of any .qmd you edit.
    • Do not hand-edit _site/ — it is generated. Edit the .qmd source instead.
    • Workshop numbering is a known trap — confirm the _quarto.yml mapping before assuming a website “Workshop N” lives in folder NN.
    • Two script versions: when fixing/teaching, keep *_main.R (student) and *_master.R (solution) consistent unless an intentional gap is being preserved.
    • Large binaries (.rds compiled models, _outputs/*.RData fits, slide PDFs, paper.pdf) are committed deliberately. Do not delete or regenerate them casually — see §11.
    • Publishing the site and the paper are outward-facing — do not run quarto publish, push, or trigger the PDF/publish workflows without explicit user confirmation.

    8. Content Notes

    • The website is the canonical artifact; slides/ are the historical source and may lag the website.
    • paper.md (JOSE target) and paper_psyarxiv.md (preprint) are near-duplicates — when editing the manuscript, check whether a change needs mirroring across both, and keep paper.bib / paper_psyarxiv.bib in sync.
    • The course cites a large literature (paper.bib); when adding claims, cite consistently with existing style.
    • Known small typos exist in prose (e.g. “distibrutions” in README) — fix opportunistically, don’t chase exhaustively.

    9. Tracking Changes

    • TASK.md — phase-organised task tracker with status markers (✅ done / 🔄 in progress / ⬜ planned / ❌ blocked). Update it as work progresses.
    • SCRATCHPAD.md — append-only working notes; one dated section per working session.
    • Memory files live outside the repo at ~/.claude/projects/-Users-aamirsohail-Documents-GitHub-other-BayesCog/memory/ (MEMORY.md, project_design.md, codebase_notes.md).

    10. Trigger Phrases

    "continue" — same session, context active:
1. Read last SCRATCHPAD.md entry; 2. Read TASK.md active tasks
3. Give one-paragraph recap; ask user to confirm or redirect before proceeding

"resume" — new conversation, context reset:
1. Read memory/MEMORY.md, memory/project_design.md, memory/codebase_notes.md
2. Read TASK.md; 3. Read only the last dated section of SCRATCHPAD.md
4. Report: project summary / current state / last session / active tasks / next step
Then ask the user how they want to proceed.

"update memory" — end of any session:
1. MEMORY.md — update Current State and _Last updated
2. TASK.md — move completed tasks; add new tasks
3. SCRATCHPAD.md — append new dated section (done/findings/decisions/unresolved)
4. project_design.md — only if scientific design or data structure changed
5. codebase_notes.md — only if new bugs/patterns or pipeline/model code changed
Tell user which files changed and give one-line session summary.

    There is also a project command /status (concise task summary), /resume, and /update-memory in .claude/commands/.

    11. Code Generation Best Practices

    • Read before modify. Read any .qmd, .R, or .stan file fully before editing it.
    • Minimal, targeted changes. Don’t refactor surrounding prose or code when making a fix.
    • Scientific/pedagogical rigor. Don’t fabricate statistics, parameter values, or model outputs. If you change Stan or R code, verify it still runs and produces sensible results — don’t just check that it parses. Keep teaching explanations correct, not just plausible.
    • Reproducibility. No hardcoded absolute paths; respect renv; set seeds where a script relies on one.
    • Preserve the student/master split and the deliberate bugs in 09.debugging.
    • Never delete committed binaries (*.rds, _outputs/*.RData, *.rda, paper.pdf, slide PDFs) without explicit confirmation — .claude/settings.json denies this by default.

    12. Context Management

    • Start a fresh conversation with resume (or /resume) to reload memory + tasks.
    • Use continue mid-session to re-anchor on the last scratchpad entry.
    • End substantial sessions with update memory to persist progress.
    • Use /compact when context grows long; the harness will summarize and continue.
